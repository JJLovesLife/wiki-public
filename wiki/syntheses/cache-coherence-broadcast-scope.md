# Cache Coherence Broadcast Scope

## Question

要保持 cache coherence，是不是意味着所有写都要广播给所有核心？

## Answer

不是。Cache coherence 要求的是同一个 cache line 的写入有一个所有核心都能遵守的顺序，并且旧副本不能继续被当作最新值使用；它不要求每一次 store 都把新值广播给所有核心。

典型情况可以分开看：

1. 如果写入核心已经拥有该 cache line 的 writable ownership，例如 MESI-like 协议里的 `Exclusive` 或 `Modified` 状态，那么后续普通 store 可以直接写本地 L1/L2 cache。此时通常没有“每次写都通知所有核心”的动作。
2. 如果写入核心只有 shared 副本，或者还没有该 line，它需要先发起 ownership upgrade 或 read-for-ownership。协议会让其它相关副本失效、更新，或者通过目录/仲裁点确认没有冲突副本。获得 ownership 之后，写入才可以提交到本地 coherent cache 状态。
3. 如果另一个核心之后要读这个 line，它会通过 coherence 协议拿到当前版本，可能从拥有 modified 副本的核心转发，也可能从 LLC、home agent 或内存层次中拿到。

所以通信通常发生在 ownership 转移、shared 副本失效、dirty line 被请求、writeback 等边界上，而不是每一条普通 store 都广播一次 value。

“广播”也要区分协议类型。早期或小规模 snooping 系统可能把 coherence 请求放到所有 cache 都能观察到的总线或互连上，这看起来像 broadcast snoop。但现代多核系统常用 directory-based coherence：目录或 home agent 记录哪些 cache 可能持有某个 line，只向实际 sharer 发送 invalidation，或者直接确认没有其它 sharer。这样 coherence 仍然成立，但不需要把所有写都发给所有核心。

Invalidate-based coherence 更常见：写者获得 ownership 时让其它 sharer 的旧副本失效，而不是把每次写的新值推送过去。Update-based coherence 会把新值更新给 sharer，但这不是维持 coherence 的唯一方式，且对高频写入通常浪费带宽。

简化成一句话：coherence 需要“写权限和旧副本状态被正确协调”，不需要“每次写都全核广播”。
